## Vault and platform retention

The [July 12 canonical architecture decision](ENCRYPTED_LOCAL_VAULT_V1_CANONICAL_ARCHITECTURE_DECISION.md) is authoritative, with status `CANONICAL_ARCHITECTURE_SELECTED_IMPLEMENTATION_BLOCKED`. Retain its requirements:

- Multi-artifact app-controlled live vault: minimal public header/wrapped-root envelope, one authoritative encrypted authenticated manifest, opaque encrypted records, staging, quarantine/recovery.
- Argon2id derives an exactly 32-byte KEK that wraps a random exactly 32-byte vault root. HKDF-SHA-256 separates manifest, metadata, and secret roots and derives per-record keys. The root is not used directly for AEAD. XChaCha20-Poly1305 requires fresh random 24-byte nonces.
- Header authentication comes from wrapped-root AEAD associated data; no separate persisted header HMAC. Preserve generic public unlock failure and non-circular header context.
- Strict bounded big-endian ordered fields; reject unknown/duplicate/trailing input and unknown feature bits; checked allocation arithmetic and fixed nonrecursive nesting. Public header limit is 65,536 bytes, encrypted manifest 16,777,216 bytes, manifest entries 65,536, and individual record plaintext/ciphertext payload 4,194,304 bytes before bounded envelope overhead.
- Install and flush records before atomically replacing the encrypted authoritative manifest as the final commit point. Durability failure blocks persistence. Corruption handling must be fail closed and nondestructive by default.
- Opaque provider-owned handles, owned-copy sensitive byte classes, redacted output, best-effort clearing, and mandatory selected `VaultCryptoProvider` routing. Linux remains passphrase-first; OS keyrings are not primary storage. Backup/export has a separate format/key hierarchy.
- A consistent old whole-vault snapshot cannot reliably be detected without an external monotonic anchor. No such anchor or complete rollback-prevention guarantee exists.

Keep `DisabledVaultCryptoProvider` as the sole production selection and `productionProviderSelectable=false`. Create/open/unlock/encrypt/decrypt, active sessions, runtime secret keys/nonces, canonical parsing/file I/O, secret and sensitive-metadata persistence, sync, signing, broadcasting, and mainnet remain blocked. Do not confuse this with a claim that no executable crypto exists in the repository.

The [reconciliation audit](ENCRYPTED_LOCAL_VAULT_V1_FORMAT_PARSER_CRYPTO_RECONCILIATION_AUDIT.md) identifies production-compiled public container/manifest parsers, serializers, direct Argon2/HKDF/HMAC/AEAD helpers, commonMain fixtures, and a public integrated KAT harness. They have no app/storage integration. `SkaldVaultV1ContainerFormat`, `SkaldVaultV1ManifestFormat`, `SkaldVaultV1HeaderCommitment`, `SkaldVaultV1RecordAead`, and their supporting graph are `PRE_RELEASE_PROTOTYPE_P0_UNSUPPORTED`; the 64-byte root/header-HMAC design is not canonical. `EncryptedVaultWorkingParser` is `SYNTHETIC_TEST_CONTRACT_CLASSIFIER_ONLY`, not a canonical parser. Existing test-source public KAT implementations remain confined to their existing scope. Preserve evidence initially and review quarantine separately; no compatibility or Bitcoin-to-Monero vault migration promise exists for developer P0 bytes.

Exact canonical magic, field IDs/framing, header AAD, passphrase normalization, envelope overhead, provider API alignment, and final device KDF parameters remain deferred. Monero engine convenience cannot choose them implicitly.

Retain Android/Linux entry-point mechanics, Compose theme and generic controls, package identity, Android backup prohibitions, Gradle wrapper/toolchains, test diagnostics, `SourceGuardCorpus`, and build-local jpackage temporary-directory behavior. ## New boundaries and blockers

The [boundary decision](MONERO_WALLET_BOUNDARY_DECISION.md) is the detailed proposed contract. The required separation is:

| Boundary | Responsibility and hard blocker |
| --- | --- |
| Skald wallet domain | Own amounts, network identity, capabilities, provenance/completeness, recovery and review states without JNI/RPC/native types leaking into UI or persistence. |
| Local engine / platform bridge | Own local keys, scanning, spend detection, construction and signing. Engine choice requires demonstrated Android/Linux lifecycle, packaging, storage isolation and bounded state export. |
| Full-node adapter | User-selected `monerod` chain-data/relay service. Local scanning/signing; no seed, spend or view key sent. Default endpoint unconfigured; no public fallback or daemon management assumed. |
| Optional LWS adapter / disclosure gate | Server scanning with protocol-specific view/scan-key exposure. Consent binds wallet, normalized endpoint, protocol/key scope and warning version before any wallet-specific request; changes invalidate it. No spend key or recovery seed disclosure. |
| Transport | Credentials separate from endpoint/route policy; bounded requests/responses, TLS verification, no redirect-mediated key disclosure, cancellation/deadlines, fail-closed Tor/proxy route and DNS handling. LAN/loopback exceptions remain undecided. |
| Session/persistence/operations | Vault-authorized opaque handles; lock invalidates work and disclosures. All engine commits use approved encrypted persistence. Build/sign/relay approvals are distinct; no returned signed blob implicitly relays. |

Engine storage is a selection blocker: inventory native wallet key files, caches, databases, autosave, temporary artifacts, logs/crashes, default directories, callbacks and persistence on close. Native encrypted wallet files are not automatically canonical Skald records. Memory export or a subordinate encrypted blob adapter needs explicit review against limits, authentication, atomic commits and crash recovery; a large cache cannot be assumed to fit a 4 MiB record. No engine writes while Skald persistence is disabled. `monero-wallet-rpc` is a key-bearing wallet service, not the daemon; it is not selected as the native architecture.

LWS disclosure is irreversible in practice: disabling it or returning to full-node scanning cannot make a server forget an already disclosed view key. Consent does not authorize spend, signing, relay or bypass missing vault/provider gates. No preselected/global-forever consent, background enrollment, key-bearing health check, automatic daemon-to-LWS fallback or redirected key submission. Protocol version, subaddresses, outgoing-spend/key-image completeness and disclosure scope require a pinned compatibility review. Consent/disclosure history is sensitive metadata.
