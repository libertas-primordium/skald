## Root-envelope commitment: exact scope and limits

The [format §5](ENCRYPTED_LOCAL_VAULT_CANONICAL_V1_FORMAT_SPECIFICATION.md#5-root-wrapping-and-separated-key-commitment) defines the complete construction. The KEK is extracted using the stable vault ID, then distinct HKDF info domains derive Kwrap and Kcommit. Canonical H includes the outer magic/version/final length, all parameter/identity/profile/nonce values and every field header, excluding only ciphertext/tag/commitment values. Root XChaCha AEAD authenticates the wrapAAD framing of H. The outer HMAC authenticates its distinct domain plus LP(H), LP(C) and LP(T). Its full output is persisted, compared in constant time, and must match before attempting root AEAD open. Both checks must succeed before a root capability exists; the manifest must then authenticate and validate before session authority.

H depends only on known lengths and pre-encryption fields. It omits C/T/commitment values; HMAC is computed after C/T exist and excludes its own value. That separation removes circularity without zero-filled pseudo-fields. The commitment field's header is authenticated; its value is verified independently. Content hierarchy/AAD binds stable vault/suite identity and record context, not credential-dependent envelope material. Credential rewrap preserves content bytes but cannot revoke an older header/credential copy.

This is an **application profile requiring dedicated cryptographic review before production**. It is not a newly standardized primitive or a formal proof. The requirement is key commitment at the header/root-envelope boundary; this document does not claim unmodified XChaCha20-Poly1305 is key-committing or that each record obtains independently committing-AEAD semantics. An output length is not a proof of a matching security level: a 32-byte HMAC is not evidence of 256-bit key-commitment security. Ordinary MAC unforgeability alone is insufficient to establish commitment.

Wrong valid-profile credential, outer commitment mismatch and root AEAD authentication failure share `AuthenticationFailed`; failed stages, tags and partial root bytes are never public. Malformed public structure can be rejected before KDF, and identical end-to-end timing across public-invalid and authenticated paths is not claimed. No fast pre-Argon verifier is added.

### Published guidance versus Skald choices

[Libsodium's AEAD “Robustness” guidance](https://doc.libsodium.org/secret-key_cryptography/aead#robustness), verified 2026-10-11, describes an outer keyed hash over nonce/ciphertext/tag, also binding adversary-controlled associated data, verified before decryption. That motivates this check ordering and coverage. Skald's exact framing, field registry, separated HKDF keys, domains, stable identity and H construction are application decisions here; the guidance does not certify this entire profile. The page has no numbered normative release; retrieval date is the citation identity, not a chosen libsodium dependency.

[RFC 5869 §§2.2–2.3 and 3.2](https://www.rfc-editor.org/rfc/rfc5869.html#section-2.2), May 2010, defines HKDF extract/expand and the info context. Skald selects SHA-256 and the specific hierarchy/domain inputs. [RFC 9106 §3.1](https://www.rfc-editor.org/rfc/rfc9106.html#section-3.1), September 2021, supplies Argon2's v1.3 inputs and memory rounding semantics; the format forbids rounding aliases and separates representable costs from execution eligibility. These are not a new universal calibration recommendation.

[RFC 9771 §§4.3.2–4.3.3](https://www.rfc-editor.org/rfc/rfc9771.html#section-4.3.3), May 2025, distinguishes full commitment and key commitment; the two properties are not interchangeable. Ordinary wrong-key regression tests do not prove either property for this application construction. All cited primary references were checked 2026-10-11; source URLs/retrieval hashes where available are retained in the phase evidence. No primary document is claimed to provide independent Skald-specific canonical vectors.

## Credential decision and platform independence

The user approved NFC-normalized strict UTF-8; significant ordinary spaces; rejection of malformed/control/invisible formatting input; a create/change minimum counted after normalization; and a normalized byte maximum. The [format §10](ENCRYPTED_LOCAL_VAULT_CANONICAL_V1_FORMAT_SPECIFICATION.md#10-credential-profile-1) is the authoritative profile registry and exact property/bound definition. OPEN validates that profile and its resource/byte limits without imposing the current creation minimum. No fallback normalization or old password parser is attempted. The syntactic minimum is not an entropy estimate: repeated allowed characters or spaces are not silently rejected by an invented strength rule.

The pinned [UAX #15 revision 53](https://www.unicode.org/reports/tr15/tr15-53.html), Unicode 15.0.0, dated 2022-08-17, plus the exact six UCD files/hashes in the format define reproducibility. The [current annex](https://www.unicode.org/reports/tr15/) reports Unicode 18.0.0/revision 58/date 2026-08-12 when checked 2026-10-11; that explanatory page cannot update profile 1 data. Platform-default category tables and normalization versions must not become hidden persisted semantics. No normalization library, runtime dependency, UI input pipeline or executable credential validator is added in this pass.

## Conditions still required before production

Documentation review and arithmetic checks are specification evidence only. Before any provider enablement, a separately authorized implementation must supply independently checked primitive and complete-transcript vectors, commitment threat analysis of this exact separated-key construction, purpose-specific ownership/API review, constant-time comparison and failure-path evidence, Android/Linux profile byte parity and approved KDF/RNG behavior. The acceptance plan allocates these responsibilities without claiming they have run.

Freshly created roots remain pending until initial manifest and storage commit. Header authentication alone is not an unlocked session. Current-snapshot authority, revocation and in-flight cancellation must prevent stale results becoming readable/committable. Future storage must prove atomic visibility and crash durability separately. Full-snapshot rollback and retention of old headers remain explicit limits, not promises hidden by generation counters or passphrase rotation.

No executable file, test, source membership, build/dependency/resource, UI, admission rule or operational truth value changes in Phase 02. Prior Phase 01 test/device/package results remain historical evidence and are not reported as rerun here.
